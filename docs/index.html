A PIX-style payment gateway built to prove three things under real failure, not just describe them: idempotent intake that survives a race, an outbox that never loses an event, and a ledger that never ends up with half a transaction posted. Everything on this page is a real run, not a mockup.

How it works

two services, two databases

No shared schema, no shared connection pool. The two services are coupled only through the JSON contract on the transactions.created topic — everything else about how each one stores its own state is a private decision.

Three decisions, not defaults

Idempotency by constraint

A "check, then insert" has a race — two concurrent requests can both pass the check first. The real guard is a UNIQUE constraint on idempotency_key; the loser's insert fails and falls back to reading the winner's row, in a separate transaction, since Postgres won't let you read after a failed statement in the same one.

TransactionService.java

Outbox over dual-write

Writing to Postgres and publishing to Kafka can't both happen atomically by default. The event is written to a table in the same transaction as the business row, then a poller dispatches it — so a crash mid-publish leaves a retryable row, not a lost event.

OutboxDispatcher.java

At-least-once as the normal case

Kafka redelivers. A transaction always produces one DEBIT and one CREDIT entry; a unique constraint on (transaction_id, direction) means a redelivered message collides and rolls back before the second insert — never half a pair.
